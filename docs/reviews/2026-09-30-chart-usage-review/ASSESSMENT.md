# 图表配色与 usage 持久化告警评估

Author: Zeno Ren

日期：2026-09-30。配色修改已在本地实现；持久化部分为只读调查与建议，不包含后端行为、生产配置或 OpenClaw 自动化变更。

## 结论

需要优化告警解释和故障诊断。当前证据是间歇性写入失败后恢复，不能把失败计数称为丢失笔数，也没有证据支持紧急重启、扩大 I/O 超时或更换存储。用量仍先入易失内存，进程/节点在待写期间消失的剩余风险没有解除。

三次 `backend_ready=1`，待写批次/在写标志均为 0，失败计数未增加，成功批次和确认事件继续增加。后两次都是刚产生的短期待写，不能解释为同一事件持续积压。`backend_ready` 只表示最近观察到的持久化状态，不是主动数据库健康探针。

当前容器日志中有三次 `_periodic_flush` 错误，分别为 **21:19:48、22:00:59、22:34:10**，与当前失败总计 3 相符。见 [去敏日志摘要](usage-log-summary.json)。通知中的“新 Pod 首小时 2 次”与前两条时间吻合；通知所述旧 Pod 5 次没有在本次重新取得旧进程现场证据。

这只证明本进程已接收的事件在采样时确认追平/持续写入，不证明旧 Pod 从未丢事件、所有请求都提供了 usage，或供应商账单已经完整对账。两个 Pod 的 counter 必须按生命周期独立计算，不能直接相减或比较绝对值推断版本回归。

## 计数与现有保护

`flush_failures_total` 在一次 `_flush()` 捕获异常时加一：可能是连接、读取旧日数据、保存批次或事务提交失败。一次失败可能涉及多个事件，同一批次也可能失败多次。它不是失败事件数或最终丢失数。

失败事件保留在 pending 中，后续通常等待 30 秒再重投同一固定 batch ID。MySQL 账本与日汇总在同一个事务提交；已提交但 ACK 丢失时，重投通过 batch ID 和 payload hash 避免重复累计。新增事件进入独立 buffer，不会被旧失败批次覆盖。此路径不重放模型推理。

正常的 1–2 条短期待写属于批量提交窗口；只有持续变老、没有确认进展、队列接近容量或发生拒绝，才显示风险在扩大。Pod 硬丢失时尚未提交的内存事件仍可能丢失，因此不能把“当前队列已追平”写成零 RPO。

现有恢复/事务/内存易失性回归本轮重新运行：**44 passed、5 subtests**，见 [测试回执](usage-regression.txt)。这包含本地 fake 事务与隔离临时 JSON/子进程测试，未在生产数据库执行故障注入。

## 明确的诊断缺口

`usage_store.py` 的错误记录只有自由文本，而 `_periodic_flush` 在 `DiagnosticFilter` 的保护范围内。自由文本被移除后，日志只剩 `lb_legacy_diagnostic`、函数和行号；当前三条线上日志都没有异常类型、MySQL 错误码或阶段耗时。本地 [过滤器复现](diagnostic-reproduction.json) 确认这一点，但不据此推断线上异常就是 timeout。

内存中的 `last_error_type` 没有导出到 `/metrics`，且成功后清空，不能事后恢复历史原因。故目前无法区分池等待、新连接、SQL/锁等待、commit ACK 或其他错误。发布准备时曾有新建数据库连接超时的记录，只能作为调查线索，不是这三次失败的根因证明。

## 建议顺序（尚未实施）

1. **补结构化诊断。** 在保留自由文本过滤的前提下，增加固定事件名、后端类型、受控异常类型/数值错误码、失败阶段和耗时、批次事件数、待写年龄，以及恢复事件。历史最后失败时间/类型与当前健康状态分开保存；禁止输出凭据、连接串、SQL、事件 payload 和模型正文。保留 v2 契约，新增字段先走 v3 或安全日志，并覆盖 timeout、断连、ACK 丢失与秘密不泄露测试。
2. **改告警为分级状态。** 失败增量仍记录，但“已追平”和“持续积压”分开报告；按 Pod UID + container start time 划分序列，采集失败/缺指标保持 unknown。建议初始阈值为：有待写且最旧年龄超过 120 秒、跨多个成功采样持续出现时 warning；超过 5 分钟或拒绝计数增加时 critical。实际阈值需结合采样周期与正常写入延迟校准，小时采样无法证明分钟级持续性。空队列不能因最后成功时间较旧而误报。
3. **有原因后再改连接或重试参数。** 若证实 stale connection，再针对性评估连接验证/回收；若证实锁等待或慢提交，先查事务耗时、批次与数据库指标。不能仅凭总计 3 次就放大超时、重建全部连接或高频重试。
4. **按业务承诺决定 durable outbox。** 若用量用于强一致结算、要求跨 Pod/节点故障不丢已接收事件，单独设计可耐久 event/batch 队列、恢复重投和确认清理。若仅为运维估算，可先接受已说明的易失边界。数据库账本幂等不能代替 outbox，容器临时磁盘也不能承诺节点故障零丢失。

建议的告警文案：

> usage 批次写入出现重试：本 Pod 累计失败 3 次，随后写入恢复。22:56 快照已确认 279/280 条已接收事件，剩余 1 条约 2 秒，拒绝为 0；未见持续积压。失败次数不等于丢失笔数。当前缓冲仍为易失内存，进程在未刷盘时消失可能丢账；具体失败原因待补结构化诊断。

此文案为建议，没有向 OpenClaw 或其他渠道发送，也没有修改其 watcher、调度或历史。
