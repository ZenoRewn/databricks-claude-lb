# SSE 验收标记误判：修复与证据边界

Author: Zeno Ren

日期：2026-09-21。

## 用户报告的生产情况

用户报告：验收窗口内 Opus 5、GPT-6 Astra、GPT-4.1 的三条生产账本记录均为 `completed`；原 Pod 已被回滚删除，原始探针回执缺失。当前旧版正常在线，3 个节点和发布控制器被保留。本轮没有连接 AKS、查询生产账本或变更这些资源，因此这些状态是用户提供的信息，而非本轮现场核验结果。

这些记录支持“验收误判”的判断，但不能证明 SSE 分段是本次发布失败的唯一原因。账本中的生成完成，不等于回答内容符合探针要求，也不证明所有发布阶段均通过。缺失原始回执的事实保留，不用本地重现补写生产成功回执。

## 本地确认的缺陷

原验收器在整个原始响应中搜索 `LB_OK`。三个 API 的合法输出若拆成 `LB` 与 `_OK`，终态成功仍被拒绝。反过来，即使真实回答是其他内容，只要元数据含该标记，原逻辑也可能误通过。

新增测试在修复前实际复现上述问题：7 个失败，包括三个协议的分段误拒绝与元数据误通过。测试使用 MockTransport、临时文件和合成账本，没有发送真实模型请求。

## 修复

- 使用既有 SSE framing 和终态判定，按协议提取文本片段；兼容单字节传输拆分、LF/CRLF/CR、BOM、心跳和 JSON 转义。
- 只在生成文本中匹配标记，且要求成功终态；工具参数、元数据、其他 Chat choice 不能替代主回答。Responses 完整快照不与 delta 重复累加。
- 非流式同样改为检查协议正文，而非 JSON 原始字符串。
- 验收缓存按 0600 权限原子更新，保留可用的请求 ID、完成状态、标记是否匹配、文本长度/hash 和安全错误码，不存原始输出。
- 业务 exec 非零后只读缓存，不发起第二次推理；再次检查 Lease、Pod UID 和计划 hash。失败摘要由原状态机先持久化，再进入恢复；未完成或执行未知不会标记成功。
- 独立 QA 发现的“已有失败缓存返回退出码 0”问题也已补测试修复。只读 `receipt` 返回 0 不代表业务成功；pending 状态继续由 `verified=false` 标明。
- 本地 Kind 上游夹具默认拆分标记，使后续演练能够覆盖本缺陷。

## 验证与未验证

最终本地回归、候选应用/协调器镜像身份与测试结果见 [validation.json](validation.json)。失败测试和通过日志分别保留。独立只读 QA 完成了限定范围复核，不代替生产验收。

本轮没有部署、运行真实供应商探针、重放原失败请求或重新执行 Kind 故障矩阵，也没有删除保留的 3 个节点、控制器或任何生产资源。文本重组修复位于应用镜像；新增协调器持久回执能力位于协调器镜像，下次发布需分别固定并验证对应版本。

如果 Pod 在只读回执取回前已经消失，或 ConfigMap 写入失败，仍可能缺少证据。新增回执是结构化诊断摘要，不是完整原始 SSE 的归档承诺。
