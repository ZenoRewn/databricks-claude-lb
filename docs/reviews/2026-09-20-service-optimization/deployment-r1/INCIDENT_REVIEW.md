# 维护 selector 遗留事故：补充复盘与整改顺序

Author: Zeno Ren

日期：2026-09-20。输入：用户提供的《AKS-LB-更新失败复盘与标准化发布手册》、本任务原始工具记录、本地发布脚本和回执。

**结论：本次中断由本任务的发布编排缺陷造成。关闭流量、排空和恢复流量分属两个独立脚本；第一个脚本正常完成后留下维护 selector，第二个脚本尚未执行。不能归因于新版应用启动失败。** 用户已完成恢复及后续升级；本轮只进行本地复盘和离线验证，没有再次访问或修改 AKS，也没有推送 GitHub。

## 2. 直接原因与潜在风险必须分开

直接原因是跨脚本交接没有可靠接管者：`gated → drained` 成功退出之后，生产仍处于不可服务状态，但恢复路由的责任留给了后续一次交互式工具调用。

以下为原脚本的相关控制流：

```python
# 第一阶段
try:
    wait_for_drain()
    success = True
finally:
    write_journal()
    if not success:
        restore_service()
# 第二阶段在另一个脚本中，必须另外启动。
```

这里即使有 finally，也不能保证维护收尾。离线复现实际使用了经环境名脱敏的历史脚本逻辑，并拦截全部外部命令。

| 离线场景 | 复现结果 | 性质 |
|---|---|---|
| 修正前遇到 null endpoints | TypeError，调用一次恢复路由 | 对应第一次失败路径 |
| 排空成功，后续执行者没有接管 | 正常退出，gate 保留，恢复调用为 0 | 与第二次遗留维护状态相符 |
| 观测失败，随后日志文件写入也失败 | 恢复调用为 0，gate 保留 | 新发现的潜在风险，未声称在线上发生 |

结果见 [离线回执](gate-failure-reproduction.json)，复现入口为 [reproduce_gate_failure.py](reproduce_gate_failure.py)。这证明旧设计的缺陷，**不代表新的安全发布器已经实现或验收**。

原 `rollout.py` 还存在未在线上执行的风险：写请求超时后依赖本地 `changed` 标记判断是否已变更；回滚步骤抛错可能跳过后续路由处理；部分状态和端点数量硬编码；安全条件使用可被 `python -O` 禁用的 assert。应在新发布器中一并消除。

## 3. 应按这个顺序整改

### P0：先让维护流程可以可靠结束

1. **一个发布责任范围覆盖完整切换。** 关闭新流量、排空、停止旧 writer、启动新版本、验证、恢复全部入口、业务验收和失败收尾，必须由同一受控发布任务持有。维护期间不得等待 agent 的下一轮回复、临时编写脚本或人工启动下一段命令。确需移交时，接收者必须确认接管并获得持久状态，不能仅留下一个文件。
2. **重新定义成功。** 排空成功只进入中间状态。成功终态至少要求原路由已恢复并读回、存在预期可用端点、公网业务和用量落库验收完成。回滚后恢复可用应标记为 `rolled_back`；遗留 gate 或收尾失败只能标记为未完成/需接管。
3. **维护前验证观测通道。** 公网检查必须先拿到可信的正常基线，不能把一直报 URLError 的后台进程当成监控已就绪。采集失败要记录经过脱敏的失败阶段和原因，并阻止进入维护；不要关闭 TLS 校验来取得绿色结果。
4. **准备完成后才开始计时维护。** 固定镜像、补丁、测试脚本、完整入口清单、恢复材料和维护预算，在接流量状态下准备并验证。维护具有统一截止时间；每次 subprocess/API 调用也需有剩余预算约束。超过预算不等于允许强杀长请求，应执行预先选定的恢复或接管路径。
5. **日志失败不能跳过恢复判断。** 对恢复动作和回执写入分别捕获错误，保留两类结果。关流量前写不下恢复材料，应直接拒绝进入维护；进入维护后，即使日志介质失败，也必须尝试依据已保存状态执行安全的恢复检查。

### P1：执行器丢失或多人操作时，也不会遗留无主维护状态

1. 唯一 release ID 加受控发布互斥；跨机器不能只靠本地文件锁。每个写操作都检查对象 UID、当前 resourceVersion、预期完整 selector/原值和发布所有权。
2. 持久记录操作意图、API 执行结果及读回状态。ACK 丢失时先读回，不能根据返回码或内存布尔值猜测是否写入成功。重启后能从现场和回执恢复状态。
3. 引入独立恢复检查者。失去发布心跳或超过维护预算时，核对所有权、schema、writer 状态和后端健康，再选择恢复或告警。**TTL 到期不应无条件打开流量。** 用户或其他执行器接管后，旧发布者必须失去写入资格。
4. 自动发现全部 Service、Ingress 和其他接入路径。原脚本只控制了一个 Service，用户手册记录了两个；这说明原检查未证明维护覆盖全部入口。空、缺失、null EndpointSlice 分别按显式规则处理；未知观测不可当成零在途。
5. 优先利用应用准入和排空状态，同时检查活动请求、队列与尾批落库。selector 摘流和一次 active=0 都不能证明所有已有连接停止。新版 drain 是进程内不可逆状态，不能删除 marker 就假定旧进程重新可服务；恢复前必须验证 `/health/accepting`。
6. 单写者模式明确验证旧 writer 已退出；`maxSurge=0` 不保证终止中的旧进程已经停止写入。节点失联或迁移不兼容时单独处理。

### P2：再减少发布本身对用户的影响

在新旧用量语义、会话行为和调度容量验证通过后，再选择双副本滚动或蓝绿。当前故障首先是维护收尾失控，增加副本不能自动修复它；selector 选不中任何 Pod 时，更多副本仍无法服务。

保留既有观测与接入范围，后续给发布系统增加三类检查：维护超预算、后端 Pod 可用但 Service 无合格端点、路由恢复而公网合成业务失败。本轮不创建或修改 OpenClaw 任务。

## 4. 发布器必须具备的离线验收

| 注入点 | 必须满足的结果 |
|---|---|
| gate 后、排空后、旧 writer 停止后、新版 Ready 后中断 | 不出现无人持有的 gate；可从持久状态恢复或明确升级接管 |
| API 已写入但 ACK 丢失 | 读回确认，避免盲目重复写入/回滚 |
| EndpointSlice 缺字段、null、空列表、terminating/非 Ready 端点 | 解析明确；无法确认时禁止当成通过 |
| 日志磁盘满、证据路径不可写、恢复 API 返回失败 | 不吞掉错误，不跳过安全恢复判断，不返回成功 |
| SIGTERM、SIGKILL、执行器主机丢失 | 前者检查清理，后两者验证独立恢复机制；不能只测试 finally |
| 两个发布者并行、人工先恢复了 Service | 旧持有者停止写入，不覆盖新的 selector 或版本 |
| 新版已接流量后回滚 | 排空新版并保护新增用量；保留追加账本，不恢复旧快照覆盖新记录 |
| 最后一个验收步骤失败 | 最终回执仍为未完成/回滚，不能因 CI 或 Pod Ready 为绿就报告发布成功 |

发布器的测试应与应用单元测试分开。先在 mock 和临时 Kubernetes 集群中演练，再依据明确的变更范围决定是否安排生产验证。
